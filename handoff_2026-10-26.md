### 2. When the fine-tune pilots finish

```bash
cd /raid/colivares/github_repos/gan_bpm_next/condor
grep -E 'completed successfully|failed with status|EXITING' finetune.dag.dagman.out | tail -6
for f in log/finetune_rcbf_wgan_s0.*_fm0.pilot.*.out; do echo "== $f"; sed -n '/metrics.csv: epoch/,/^====/p' "$f"; done
```

The second command prints each pilot's health table. **Healthy** (`ext_gan_plan.md` §2.4): the
adversary's share within 0.5–2× its target in ≥ 80 % of epochs; the critic gap neither running
away nor collapsing to 0. Then score both against their start:

```bash
MX=/radraid2/colivares/matrix/gan_bpm_rcbf_f13uclav2
condor_submit core_check.sub -append "args = --fold 0 --run-dir ${MX}_adv0_ext500_e40_f0 --run-dir ${MX}_ft_wgan_s0p2_ext500_e20_f0 --run-dir ${MX}_ft_wgan_s0p5_ext500_e20_f0"
```

The scorer sees two fine-tunes that warm-started from the first run and applies §2.6: a win needs
Dice at 0.3 up with a 95 % CI above 0, the called core ≤ 1.25 × the label's (median), mean
matched Dice not below the start's, brain MAE ≤ 1.25 × the start's. Its last line is `PICK:`.
Then per §2.5: 2B (`finetune_cell.sub -append 'ARM = ragan' …`) if 2A is unhealthy or no
better; 2C (feature matching); 2D (`scripts/interpolate_weights.py` on the best); 2E (all 5
folds), which first needs λ_ext = 500 on all 5 folds (`ext_sweep_cell.sub -append
'LAMBDA_EXT = 500' -append 'MODE = full'`, about a day of one GPU). Start that only once a
fine-tune wins.

## What was found and changed today

- **gan_bpm step 1 (D-98 result): λ_ext = 500 is the pick**, by the pre-declared rule (fold 0,
  90 held-out cases, `last.pt`): Dice at 0.3 0.366 → 0.385 → 0.402 for λ_ext 50 / 200 / 500,
  +0.035 [0.022, 0.050] over the control, MAE ×1.03. **It moved the level, not the place:**
  matched 0.445 → 0.451 (CI includes 0), spread 0.91 → 0.97, called core 0.51 → 0.67 of the
  label's; cut at 0.4 all three score 0.43. All three are below the matrix's early-stopped
  adv0 model (epoch 7: 0.412 at the cutoff, matched 0.470), which was selected on these same
  cases. Place (about half the core found) remains the main problem.
- **The scorer moved into gan_bpm** (D-100, MRDPM #39): MRDPM's version only knew §1.4's rule
  and read gan_bpm through the old checkout, which refuses `gan_mode="ragan"`. MRDPM's
  `--run-dir` stays only for the reproduction above.
- **finetune.dag's first submission failed** (status 78, every trial): `VARS ALL_NODES` sat above
  the `JOB` lines, and DAGMan applies `ALL_NODES` only to nodes defined above it, so `SOURCE`
  never reached the jobs. Fixed (`1bb910f`); `SOURCE` is set in git to the λ_ext = 500 run.
- **The three BRANs pretrained** on 35840's L40S (1822823–25: `rcbf_l1`, `rcbf_ext`,
  `rcbf_extlow`, 50 epochs, ~35 min each). Their "core Dice 0.69–0.70" is pooled over a few
  monitor patients and not comparable with the core check; `CHECK_PRE` is the comparable number.
  The H100 debug training with a BRAN (1822856) ran clean (the 87 GiB peak matches the earlier
  runs at batch 4).
- **Check output, both repos:** plain PASS / FAIL, no emojis; FAIL only means something is
  wrong (a caught broken version prints PASS); every run ends with one `RESULT:` line and only the
  failures. All root gan_bpm `_*_checks.py` and MRDPM's three check scripts;
  `zeng_isles18_eval/_helpers_checks.py` not yet (it has uncommitted edits of Carlos's).
